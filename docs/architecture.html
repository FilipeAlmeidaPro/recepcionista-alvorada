The write gate

Architecture of a Brazilian-Portuguese voice receptionist for a clinic. The thesis fits in one line: the model proposes, the code writes.

One voice turn

A call is a sequence of turns, and every turn crosses six stages. Three are network, three are local code. The gap between them is four orders of magnitude — and that is what decides where optimising is worth anything.

The gate

No write tool is ever called directly by the model. It emits an intent — a proposal — and ten rules in code decide whether it becomes a row in the database.

The arrow that doesn't exist is the important part of the drawing.

R8 — the rule that catches hallucination

The validator doesn't only receive structured arguments. It receives the sentence the agent spoke out loud, read from the transcript — not the one it claims to have said.

If it queried Tuesday and confirmed "Thursday", the entities diverge and the write is blocked, with every argument correct.

[BLOCKED]  agent confirmed the wrong day    R8_confirmacao
             └─ said weekday 3, the slot is 1
[BLOCKED]  agent named the wrong doctor     R8_confirmacao
             └─ said Dra. Larissa Nakamura, the slot is Dra. Thaís Bittencourt
[BLOCKED]  caller hesitated                 R8_confirmacao
             └─ reply «hmm, sei lá» read as «undetermined»
[WROTE]    everything checks out            rules passed: 10/10

Three things the model does not control

The orchestrator takes three decisions out of the LLM's hands, on purpose.

1. The caller's constraint

Extracted from speech by the deterministic normalizer, turn by turn. The model picks the specialty; the code picks the filter. If the constraint came from the model's own summary, R7 would be validating the model against itself.

2. The confirmation sentence

Read from the previous turn's transcript, never self-reported.

3. The write

Goes entirely through the validator. No exception, no side door.

The raw LLM scores 93%. That contradicts the premise that normalising spoken Portuguese is where everything breaks — and it changes the argument for the deterministic normalizer.

It isn't justified by accuracy. It's justified by being 660,000× faster, by consuming no quota, and by being deterministic — which is exactly what R7 needs in order not to validate the model against itself. The missing 7% alone wouldn't pay for 300 lines of parser. Latency and determinism do.

Noise isn't the problem; truncation is. That contradicts the original plan's premise. The real risk is the VAD cutting speech short, not background noise.

And the worst case isn't failing — it's being plausibly wrong. A truncated phone number becomes 1198765: a number that looks valid and isn't. That is exactly why digit-by-digit confirmation exists.

92% for a receptionist made of 150 lines of if is a bad finding, not a win. It means that with a scripted caller the suite tests the machine, not the model — the script hands over the right line at the right moment and carries a dumb agent on its back.

The discriminating power lives in the synthetic caller: a second LLM with a private goal and a personality, following no script. Scripted mode stays useful as a deterministic regression net in CI — cheap, and it never fails on a coin flip.

The limit of the gate

The validator guards the write. It does not guard the speech — and the Groq run showed exactly where that hurts:

caller: How much does an orthopedics appointment cost?
 agent: An orthopedics appointment costs R$ 200.00.
caller: And do you take Unimed?
 agent: Yes, we accept Unimed.

The system has no price table, no insurance data, and no tool for either. Two inventions, delivered with the confidence of real data, without calling a single tool — which is why the validator never fired.

Against spoken hallucination the only defence is an eval assertion. That's what caught it. It's the argument for having both layers: the gate guarantees the database takes no garbage; the suite is what discovers that the mouth made something up.

Conversations don't stay on the happy path

Sixteen of the forty scenarios have something going wrong mid-call: the caller hesitates, corrects themselves, goes quiet, interrupts, changes their mind or drifts off topic. The recovery rate measures how many still finish the task — and that's what separates an agent that leads a conversation from one that only works when everything goes right.

Deleting is the hard part

Recording a call is easy. What the law asks for is deletion, and personal data kept without a defined window is data kept by neglect. Here the window is code with ten tests, not a sentence in the README.

layerwindowwhy
transcript90 days where the health data lives — "chest pain" identifies more than an ID number
operational metadata730 days when they called, whether it booked, contact reason; runs the operation
the appointment itselfuntouched separate record, separate legal basis

What identifies goes; what manages stays. python3 -m clinica.retencao applies it; --simular shows what would go without deleting anything.

What's missing, and why

What's missing is streaming transcription. Without it the agent only starts thinking once the caller stops talking, and that is half of the perceived slowness. It needs paid streaming STT — the same conclusion the latency table had already reached from another direction.

The microphone, automatic turn-taking and barge-in already exist: python3 -m clinica.servidor opens the browser demo, with a client-side VAD that opens and closes the turn and cuts the agent off when you talk over it. Barge-in needed no Pipecat — interrupting is deciding when to stop playing audio, and turn detection is VAD; both belong on the client. The same VAD exists in Python, with fourteen tests, in clinica/vad.py.

Deliberately out of scope: insurance plans, pricing, ERP, payments, outbound calls, sales funnel. Architecture sketched for all of them, none implemented. Knowing what not to ship inside a deadline is a sign of seniority, not of missing ambition.

Why not Vapi, Retell or n8n: they hide exactly what this document shows — the per-stage trace, turn control, the validation layer. I'd be differentiating on what the tool does for me. On a short deadline in production, I'd use one. In a technical walkthrough, no.
